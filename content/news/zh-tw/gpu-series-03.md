上一講我們理清了DRAM、DDR、GDDR、HBM的關係，建立了視訊記憶體和記憶體的完整知識框架。從這一講開始，深入具體的故障。第一個深入的物件，是GPU伺服器中價值高、維修難度高、且一旦出現健康風險就容易影響業務連續性的部件——HBM視訊記憶體。H100、H200、A100、B200，用的都是它。

##  同一臺H200，同一個ECC錯誤，23天后換了機櫃又出現

一臺超微H200，nvidia-smi報了GPU ECC錯誤。CE數值不大，沒有UE，伺服器正常執行。按標準流程，在維護視窗執行reset，volatile歸零後繼續觀察，24小時內未復現，進入觀察期。

23天后，同一臺裝置，同一張GPU卡，GPU ECC錯誤再次出現。這次有一個關鍵變化：兩次故障之間，這臺裝置已經因為業務排程從一個機櫃遷移到了另一個機櫃——供電環境變了，散熱環境變了，網路位置也變了。

如果兩次都在同一個機櫃，還可以懷疑是機櫃供電波動或散熱條件導致的環境因素。換了機櫃還復發——機櫃環境因素的優先順序明顯下降，故障方向收斂到裝置自身。

這一次，不再清零觀察，直接下架送修，更換GPU單卡。

同樣是“GPU ECC錯誤”，第一次清零觀察是對的，第二次直接換卡也是對的。區分該走哪條路，靠的是對HBM視訊記憶體退化機制的理解。這一講就從這裡展開。

##  一、HBM的物理結構——為什麼它比DDR和GDDR都難修

上一講我們講過，HBM是多層DRAM晶片垂直堆疊的結構，一個HBM堆疊的內部結構，從下到上依次是：

**最底層：邏輯層（Logic Die）**。負責控制上面所有DRAM層的讀寫操作，是整個堆疊的“管理者”。

**中間層：多層DRAM Die**。H100的HBM3是8層DRAM堆疊，H200的HBM3e也是8層，B300等新一代GPU已經演進到12層。層數越高，單堆容量越大，但內層散熱路徑也更長。每一層都是一個完整的DRAM晶片，有自己的儲存單元陣列。

**層與層之間：TSV（Through-Silicon Via，矽通孔）**。數以萬計的微米級通孔貫穿每層矽片，把上下層的電路直接導通。這些通孔就是層與層之間的“電梯”——資料通過TSV在各層之間高速傳輸。

**整個堆疊坐在Interposer（中介層）上**。Interposer是一塊矽基板，在H100/H200這類SXM資料中心GPU上，GPU核心和多個HBM堆疊共同封裝在interposer上，通過基板上的精密走線互相通訊。具體堆疊數量、容量和可用視訊記憶體取決於GPU型號與產品形態。

這個結構帶來三個維修層面的直接後果：

### 後果一：故障定位精度遠低於DDR和GDDR

DDR記憶體壞了，ipmitool告訴你P1-DIMMC1，你拔出那條換一條新的。

GDDR顆粒壞了，MemtestG80告訴你哪個地址段有錯誤，你可以對應到PCB上的哪顆物理顆粒，用BGA返修臺拆下來換掉。

HBM壞了，nvidia-smi告訴你“這張GPU有ECC錯誤”。雖然NVIDIA的診斷工具在某些場景下能給出更細的邏輯定位（錯誤地址、行重對映記錄等），但對第三方維修和常規運維來說，HBM通常無法像GDDR那樣定位到可單獨更換的物理顆粒。即使能通過日誌推斷錯誤集中在哪個記憶體區域，HBM堆疊與GPU核心是通過CoWoS等先進封裝合封在一起的，無法單獨更換某一個堆疊，維修決策上也多半仍然落到整卡更換。

**大多數情況下，HBM出了問題，處理方式是換整張GPU卡。**

### 後果二：HBM堆疊熱路徑複雜，區域性熱點更難被發現

多層DRAM堆疊在一起，最內層的晶片被外層“包住”了。熱量要從內層傳導到外層、再傳導到散熱器，路徑比平鋪結構長得多。堆疊層數越多（8層→12層），內層散熱條件越差。

在高負載下，內層溫度可能明顯高於外層。HBM堆疊內部更容易形成單一核心溫度無法完全反映的區域性熱點。散熱器貼合不到位、矽脂老化失效，會提高HBM相關ECC風險，表現出來的就是ECC錯誤開始增長。

這也解釋了一個運維團隊經常遇到的問題：“為什麼nvidia-smi顯示GPU溫度看起來還好，但ECC已經在漲了？”

因為`temperature.gpu`反映的是GPU核心溫度，不一定完整反映HBM堆疊內部的最熱點。nvidia-smi還提供了`temperature.memory`欄位（部分平臺支援，不支援時顯示N/A），日常監控應同時採集兩者。如果HBM溫度長期高於GPU核心溫度，或與同型號健康卡差異明顯，應優先檢查散熱接觸、功耗、風道和負載條件。即使GPU核心溫度未超限，HBM區域性熱點、散熱貼合不良或長期熱迴圈仍可能導致ECC增長。

第7講（ECC歸因路徑）會詳細講如何判斷ECC報錯的根因是散熱還是視訊記憶體顆粒本身。

### 後果三：物理退化方向多、且不可逆

HBM相關ECC可能來自DRAM儲存單元退化、TSV微裂紋、封裝互連、interposer資料路徑或電氣/熱條件等多個方向。GPU伺服器在7×24小時執行中，反覆經歷的熱迴圈會在微米級物理結構上產生累積應力，這類物理退化通常不會自愈，長期高負載和熱迴圈會提高繼續惡化的風險。

現代GPU（Ampere/Hopper/Blackwell架構）中，引入了硬體級的行重對映（Row Remapping）機制，當某些記憶體位置被判定為退化區域時，GPU可以通過行重對映機制隔離相關區域，我們在第2講中已經做過詳細講解。GPU執行中發現退化的記憶體行時，會先標記為待處理（pending），在reset或重啟時，韌體可以通過這個安全視窗來執行行重對映，把資料路徑從退化行切換到備用行。重對映完成後，GPU重新上線時就會繞開那些區域。

但是，row remapping資源是有限的，具體上限和健康判斷以NVIDIA文件和RMA策略為準。一旦備用資源耗盡，物理退化的影響才會真正暴露。所以判斷HBM還能不能用，不能只看reset後volatile是否歸零，要結合remapped rows數量、pending/failure標誌和availability等級判斷視訊記憶體健康風險。具體檢視方法我們會在第5講中展開。

理解了這三個後果，你就理解了HBM視訊記憶體故障的處理邏輯為什麼和DDR、GDDR完全不同，**DDR是“定位→換條→驗證”，GDDR是“定位→換顆粒→驗證”，HBM是“監控趨勢→判斷階段→決定時機→換卡”**。

##  二、HBM健康風險的四類狀態

HBM視訊記憶體的退化通常是一個漸進過程，按照演進路徑可以劃分為四類狀態。在實際演進中，我們不一定能完整觀察到按順序出現的故障訊號，有的時候首次報錯就是UE，有的時候掉卡也可能來自PCIe或供電而不經過CE階段。

### 第一階段：ECC CE緩慢增長——預警期

ECC CE緩慢增長是最早期的訊號。nvidia-smi報告的ECC corrected error開始出現並逐日增加，系統執行完全正常，任務不受影響。這說明單個CE通常已被ECC機制糾正，不會像UE那樣直接造成任務中斷。但是，如果CE在持續增長，則說明硬體健康風險在持續上升，需要跟蹤增長趨勢。

這也是運維團隊容易出現的誤判，“才十幾個CE，不影響業務。”

在傳統伺服器的DDR記憶體上，偶發幾個CE可能確實沒關係。但是，**在HBM上，CE的增長趨勢比絕對數值更重要**。從每天0個變成每天10個，即使總數還不大，也說明有某個儲存單元在退化。如果趨勢不變，幾週後這個數字可能變成每天100個，然後就會在某一個階段出現UE報錯。

**處置建議**：記錄CE每天的增量（不只看累計總數），建立趨勢曲線。增量穩定為0，則大機率是偶發的軟錯誤，繼續監控。如果增量持續增長，需要進入下一階段的準備。

### 第二階段：嚴重ECC事件——告警期

UE意味著錯誤的數量或嚴重程度超出了ECC糾錯機制的能力。系統發現了問題，但無法修復。

這時系統通常會觸發保護動作，例如日誌出現Xid 48（不可糾正ECC）、Xid 94/95（contained/uncontained ECC error）等ECC相關事件，正在執行的訓練任務可能被終止。嚴重情況下，GPU可能從匯流排掉落（Xid 79），甚至整臺伺服器宕機。

### UE出現了，是不是一定要換卡？

UE有可能是硬體實質損傷觸發的（需要換卡），也有可能是驅動Bug、瞬間電壓波動等軟體或環境因素觸發的（可以恢復）。區分的關鍵驗證手段是壓測：先完整留存日誌和計數，再在維護視窗內執行reset/重啟，使volatile計數重新開始觀察，然後做GPU Burn壓力測試，24小時滿負荷執行，如果通過且volatile ECC不再累積，大機率是軟體或環境觸發的偶發事件；如果壓測中途報錯或ECC快速重新累積，確認是硬體問題。

**處置建議**：立即進入高風險處理流程，停止該GPU上的關鍵業務任務，完整記錄當前ECC狀態和日誌，在維護視窗執行reset/重啟後做GPU Burn 24小時壓測。根據壓測結果決定繼續觀察還是送修。具體操作步驟和判斷標準，我們將在第5講中展開。

### 第三階段：效能測試結果明顯偏低——功能退化期

這個階段不容易被常規監控發現，而且通常不在任務執行中動態發生。這類問題常常不是普通ECC巡檢能直接發現的，而是在同條件效能對比、DCGM診斷或業務吞吐異常中暴露。

這個階段表現出來的症狀是nvidia-smi看起來正常，但在同型號、同驅動、同配置的健康卡對比下，效能測試顯示吞吐量明顯偏低。需要注意的是，效能偏低的原因可能涉及PCIe傳輸、GPU間互聯、本地視訊記憶體訪問、時鐘/功耗/溫度等多個層面，不能用單一測試工具直接判定HBM通道損壞，必須逐項排除後才能收斂方向。具體的歸因排查流程，我們將在第6講中展開。

到了這一步，GPU還能被系統識別，還能跑一些輕量任務，但算力已經打了折扣。繼續用下去，很可能在下一次高負載時直接進入第四階段。

**處置建議**：完成對照測試和基礎排除後，如果異常仍然指向GPU本體，應退出關鍵業務並安排換卡計劃。建議在每月的DCGM全項診斷中加入效能對比測試，主動發現這類問題。

部分Blackwell及後續平臺支援更進一步的GPU Memory RAS Repair能力，但具體支援範圍、觸發條件和恢復行為取決於GPU、韌體、驅動和整機平臺。觸發GPU Memory RAS Repair，說明GPU視訊記憶體RAS機制已經介入，應視為硬體健康風險升高，而不是普通效能波動。

### 第四階段：GPU從匯流排掉落——停機期

nvidia-smi完全看不到這張卡。lspci顯示revision id為ff，或者乾脆看不到對應的PCIe裝置。

lspci是Linux下檢視PCI裝置的命令，revision id是PCI裝置的硬體版本標識欄位，ff（0xFF）表示PCI總線上讀不到裝置的有效資料，這通常意味著GPU物理上沒有正常通訊，具體原因可能是掉卡、接觸不良或硬體故障。

當HBM視訊記憶體退化演進到了這一類狀態，系統已經無法穩定訪問GPU。這可能是嚴重ECC事件後的結果，也可能來自PCIe、供電、連線或主機板問題。從可靠性交付和經濟性看，通常優先整卡更換、RMA或報廢處理。

不過需要注意：不是所有的“revision id為ff”都意味著走到了第四階段。第11講會詳細講，ff這個狀態也可能是PCIe介面接觸問題或ECC積累觸發的臨時掉線，具體的區分方法是通過重插拔或reset後能否恢復，恢復後壓測能否通過。

##  三、真實案例：同樣是“GPU ECC錯誤”，三種不同的處理和結果

以下三個案例全部來自我們維修的H200伺服器叢集，同一批裝置，同樣的執行環境。三個案例連續呈現“觀察→升級→反轉”的決策邏輯。

### 案例一：J-0629——首次ECC，清零觀察

**裝置**：H200（SXM5 8卡）

**時間**：2026年3月26日

**現象**：nvidia-smi報告GPU ECC錯誤。CE數值不大，沒有UE，伺服器正常執行，訓練任務不受影響。

```bash
# 確認錯誤型別和數量
nvidia-smi --query-gpu=index,ecc.errors.corrected.volatile.total,ecc.errors.uncorrected.volatile.total --format=csv,noheader
```

結果顯示是CE，沒有UE。裝置下架，在維護視窗執行GPU reset清除ECC計數，重新上架後持續監控24小時，volatile ECC未重新累積。

**判斷**：CE數量不大，清零後不再累積，大機率是偶發的軟錯誤。進入觀察期，繼續監控CE每日增量趨勢。

**案例重點**：首次出現CE時，清零觀察是合理的第一步處理。關鍵是清零後要持續監控volatile ECC增量，確認是否復現。

### 案例二：J-0813——23天后同裝置復發，跨機櫃，換卡

**裝置**：H200（SXM5 8卡），與J-0629為同一臺伺服器

**時間**：2026年4月18日，距案例一23天

**關鍵細節**：兩次故障之間，這臺裝置已經從一個機櫃遷移至另一個機櫃。供電環境、散熱環境、網路位置全部變了。

**現象**：GPU ECC錯誤再次出現。

**處理**：直接下架返回維修中心，更換GPU單卡。換卡後壓測通過，ECC歸零。

### 為什麼第二次直接換卡？兩條證據疊加：

**證據一：同裝置復發。**第一次清零可能是偶發，第二次復發說明“偶發軟錯誤”的可能性下降，裝置自身硬體健康風險上升。清零隻是重置計數觀察視窗，並沒有消除潛在根因。

**證據二：跨機櫃復發。**裝置遷移了機櫃位置，供電環境和散熱環境都變了。如果兩次故障都在同一個機櫃，還可以懷疑是機櫃供電波動或散熱條件差導致的ECC（第7講的歸因路徑②和⑤）。換了機櫃還復發，機櫃環境因素的優先順序明顯下降。結合ECC復發、壓測和換卡驗證，工程上將該卡判定為視訊記憶體健康風險高，不再繼續清零觀察。

**J-0629和J-0813合在一起，構成了ECC處理中最重要的決策分水嶺：**

首次出現可以做清零觀察。但是如果同裝置復發，需要考慮直接處理，不再清零等待。

**案例重點**：23天的復發間隔揭示了一個工程經驗：在這個叢集的執行壓力下，硬體退化的復發週期約為3-4周。這意味著，reset後的觀察期不能只侷限在24小時。在工程上，該類裝置的初始觀察週期可以設定為30天，其他叢集應根據負載強度、歷史復發間隔和客戶業務風險進行調整。

### 案例三：J-0493——Xid 79掉卡，但壓測通過，不換卡

**裝置**：H200（SXM5 8卡）

**時間**：2026年3月9日

**現象**：GPU3突然掉卡，系統日誌出現Xid 79和識別異常。

```text
GPU has fallen off the bus
Unable to determine the device handle for GPU3: 0000:5D:00.0: Unknown Error
```

Xid 79說明GPU從匯流排掉落。很多運維工程師看到Xid 79的第一反應是“GPU壞了，需要換卡”。

但是，這個判斷在相當一部分情況下是有偏差的。

**Xid 79是GPU從匯流排掉落的結果訊號，可能由視訊記憶體UE觸發，也可能來自PCIe、供電、驅動、溫度或連線問題。觸發UE的原因不一定是硬體實質損傷，驅動Bug、瞬間電壓波動也可能會觸發UE。區分的關鍵驗證手段是壓測。**

```bash
# 記錄當前ECC狀態（reset前必須先記錄）
nvidia-smi --query-gpu=index,ecc.errors.corrected.volatile.total,ecc.errors.uncorrected.volatile.total,ecc.errors.corrected.aggregate.total,ecc.errors.uncorrected.aggregate.total --format=csv

# GPU reset（volatile計數會隨reset歸零，aggregate不會）
nvidia-smi -r -i 3

# reset後重新記錄，觀察volatile是否重新增長
```

裝置下架，清除ECC，做24小時GPU Burn壓測。壓測全程無中斷無報錯，ECC計數始終為零。

**判斷**：壓測通過，說明該GPU在本次高負載驗證條件下未復現視訊記憶體相關不穩定。Xid 79大機率是軟體因素或瞬間環境因素觸發的偶發事件。裝置恢復上線，加強監控頻率。

**案例重點**：Xid 79聽起來比CE嚴重得多，但處理決策依然取決於壓測結果。24小時GPU Burn通過，說明該GPU在當前高負載條件下暫未復現硬體不穩定，可降低風險等級進入觀察期，但仍應持續監控，不能直接判定為永久健康。

##  四、從維修角度看運維——日常監控和處理SOP

### 每日ECC巡檢

```bash
# 建議設cron定時任務，每日自動記錄
nvidia-smi --query-gpu=index,name,ecc.errors.corrected.volatile.total,ecc.errors.uncorrected.volatile.total,ecc.errors.corrected.aggregate.total,ecc.errors.uncorrected.aggregate.total --format=csv
```

輸出的四個ECC值含義：

- `volatile corrected`通常反映當前驅動生命週期內，或最近一次reset/清零後的CE計數
- `volatile uncorrected`通常反映當前驅動生命週期內，或最近一次reset/清零後的UE計數
- `aggregate corrected`持久化歷史CE計數；Ampere及以後不支援清除aggregate計數
- `aggregate uncorrected`持久化歷史UE計數

注意：快速巡檢的`total`欄位可能彙總DRAM和SRAM錯誤，正式判斷應使用`nvidia-smi -q -d ECC`區分DRAM/SRAM分類。判斷趨勢時必須記錄取樣時間、驅動載入和重啟時間。

```bash
# 發現異常後做正式複核，區分DRAM/SRAM和行重對映狀態
nvidia-smi -q -d ECC,ROW_REMAPPER
```

對比volatile和aggregate，可以判斷這張卡的歷史健康狀態。一張aggregate數值很大但volatile為零的卡，說明歷史上累積了大量錯誤，當前驅動週期內暫未記錄新增，但不能因此認為問題已經消失。對A100/H100/H200這類支援行重對映的GPU，此時必須同時檢視Row Remapper狀態，結合行重對映記錄和趨勢綜合判斷，可以參考第2講J-1285案例的經驗。

### 週期性DCGM健康檢查

```bash
# 每週快速掃描
dcgmi health -g 0 -c
dcgmi diag -r 2

# 每月全項診斷（建議在空閒時段執行）
dcgmi diag -r 3
```

r1是快速檢查（幾分鐘），r2是中等深度（十幾分鍾），r3是全項診斷（可能需要幾十分鐘甚至更長）。我們建議，日常檢查用r1，每週檢查用r2，每月檢查用r3，具體節奏可以根據裝置數量和業務視窗調整。DCGM診斷等級、具體專案和耗時隨版本、GPU型號和環境變化，正式交付應儲存完整的DCGM報告。

##  本講小結

HBM視訊記憶體是GPU伺服器中價值高、維修難度高的部件，其堆疊結構決定了故障只能定位到堆疊級、內層散熱條件差、物理退化不可逆。

HBM退化通常是一個漸進過程，常見演進路徑為：CE緩慢增長→嚴重ECC事件→效能異常→GPU掉線，在實際演進中，我們不一定能完整觀察到按順序出現的故障訊號。每類狀態都有訊號，每類狀態都有對應的處理方式。早期CE不要恐慌換卡（浪費錢），嚴重ECC事件出現後不要繼續清零等待（耽誤事）。

三個案例總結出的工程經驗：同樣是“GPU ECC錯誤”，處理方式取決於是否復發、是否跨環境復發、壓測是否通過——關鍵不在ECC數值的大小。

**reset不是修復視訊記憶體，reset是診斷的起點。reset之後必須壓測，壓測結果才是判斷的依據。**
